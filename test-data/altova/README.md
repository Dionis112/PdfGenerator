# Корпус для разработки совместимости с Altova

Обновление 06.10.2026: `legacy-general` и `legacy-negative` проходят опциональный `altova2012-general-v1`. Ожидания и допустимые отличия — в `expected-properties.json`, уровень проверки — в манифесте v2. Строгий запуск: `dotnet run --project eng/PdfGenerator.TemplateValidation -c Release -- . artifacts/altova2012-run --strict-altova2012`. Эталоны оригинального движка пока отсутствуют; диаграммы, XBRL и современные даты остаются вне реализованного профиля.

21 пара `*.xml` + `*.xsl` с одинаковыми именами: 36 различных функций Altova, 46 сочетаний имени и числа аргументов. Дополнительно включены XBRL-схема и linkbase. Входные данные синтетические. Все шаблоны содержат реальные вызовы расширений: заглушек и обходов через `function-available()` нет.

Машиночитаемый [manifest.json](manifest.json) связывает входы, шаблоны, профили движка, виды результата и сигнатуры `имя#число-аргументов`. Отрицательные сценарии запускаются отдельно; `dynamic-error` означает ошибку внутри поддерживаемой функции, а не отсутствие расширения.

Основа сигнатур: [AltovaXML 2012, Extensions / General Functions, печатные страницы 142–144](https://www.altova.com/documents/2012/AltovaXMLRep.pdf#page=147). Версию фактического движка нужно фиксировать при снятии эталонов; совпадение с другими версиями не предполагается.

Корневые примеры, `charts/`, `xbrl/` и `negative/` используют XSLT 2.0. Диаграммы рассчитаны на Enterprise/Reporting и описаны в том же руководстве, страницы 146–149. Каталог `modern/` использует XSLT 3.0 и сигнатуры из [XMLSpy 2026: Date and Time](https://www.altova.com/manual/XMLSpy/spyenterprise/fxaltova_xpxqdatetime.html). Поддержка этих функций в AltovaXML 2012 не заявляется; современный профиль включать только для соответствующего целевого движка.

## Запуск и снятие эталонов

1. Выбрать профиль из манифеста и передать пару XML/XSLT в соответствующий процессор Altova. Положительные сценарии возвращают XML, кроме шестого (FO). Для шестого сохранить относительное расположение `../basic/parts/layout.xsl`. Современный профиль требует XSLT 3.0 и документированных расширений XPath 3.1.
2. Сохранить результат в `artifacts/altova-baseline/<имя>.xml` (для шестого — `.fo`). Рядом записать продукт, версию, редакцию, ОС, параметры запуска и настройки обработки пробелов. Эталоны пока **не сняты**; эти файлы не объявляются проверенными на Altova.
3. После реализации расширений выполнить те же пары в новом движке и сравнить с эталонами. XML сравнивать по структуре, сохраняя порядок элементов. Для RTF сравнивать точное текстовое содержимое `encoded` и `absent`, включая пробелы; отступы сериализатора не должны влиять на остальные сценарии.
4. Повторить сценарий нумерации последовательно и параллельно с одинаковыми ID в разных трансформациях. Зафиксировать поведение старого движка и проверить изоляцию состояния новой реализации. Вызов сброса включён в вывод, чтобы не прятать побочный эффект в неиспользуемой переменной.
5. Для диаграмм декодировать содержимое `image` согласно `encoding`, проверить формат и размеры, затем визуально сопоставить подписи и значения. Не сравнивать бинарные изображения побайтно между версиями рендерера. Сценарии `07`, `08`, `17`, `18` возвращают изображения в XML; сценарий `19` записывает файлы (см. ниже).
6. Каждый `negative/` запускать отдельно и сохранять код, фазу и текст ошибки. Успешный вывод `unexpected-success` означает провал проверки. Ошибка неизвестной `evaluate` означает отсутствие предпосылок теста, а не успешную проверку негативного сценария.

Расчётные контрольные точки ниже служат ориентирами для проверки данных, **не эталонами Altova**:

- `01`: входных элементов 7, структурно различных 5; `empty/@count = 0`, `single/@count = 1`, `repeated-node/@count = 1`. Порядок результата и выбор исходного дубликата зафиксировать по Altova через `identity/node/@source-positions`.
- `02`: сумма 37.5, выбран товар B; подписи `A: Бумага`, `B: Папка`, `C: Образец`; параметры `2|4|текст|7`, код узла A, пустая последовательность размера 0. Лексическое представление чисел сверить с эталоном.
- `03` и `04`: точное экранирование, результат сброса и последовательности чисел фиксировать только после запуска целевой версии Altova.
- `05`: абсолютный путь зависит от окружения; не использовать его как переносимый golden-файл. Сравнивать согласованные свойства пути, включая завершающий разделитель. Повторный вызов процессор может оптимизировать.
- `06`: итог `200.00`, две строки товаров, два разных примечания. Сначала сравнить FO, затем проверять PDF отдельно.
- `07–08`: проверить число серий/столбцов, порядок категорий, кириллицу и нулевые значения; PNG должен декодироваться из обоих представлений в `07`.
- `09–11`: каждый результат вычисляется от исходного значения, операции не образуют цепочку. Сопоставлять компоненты даты/времени, дробные секунды и наличие зоны. Поведение конца месяца фиксировать по целевой версии.
- `12`: для `leap` расчётные ориентиры — дата `2024-02-29`, время `23:59:58`, год-месяц `P3Y1M`, день-время `P4DT3H7M1S`. Это арифметические ориентиры, не снятые эталоны.
- `13`: проверить границу ISO-недели и согласованность date/dateTime одной даты, а также совпадение явного календаря 0 и перегрузки по умолчанию. Результаты целевой версии сохранить отдельно.
- `17`: в результате ожидается столбчатая диаграмма с категориями Апрель/Май/Июнь и значениями 10/0/25; состав настроек и визуальный вид сверить с Altova.
- `18`: проверить три изображения, наличие столбцов и линии, сопоставление общей категории Февраль при разных режимах merge. Поведение перегрузки по умолчанию определить по эталону.
- `19`: проверить существование двух непустых файлов и возможность их декодирования. Явный PNG должен иметь сигнатуру PNG; формат файла `.img` определить по содержимому. Элементы `saved` сами по себе не доказывают запись изображения.
- `20`: данные содержат три label-ресурса для Revenue (ru, en, verboseLabel) и ни одного для Unlabelled. Сопоставить возвращённые узлы, языки и роли; порядок и возможную фильтрацию фиксировать по Altova.
- `21`: с Revenue связаны две сноски, с Unlabelled — ни одной. Проверить текст, язык, число и порядок возвращённых узлов по эталону.

## Особенности новых сценариев AltovaXML 2012

`charts/19-save-image.xsl` требует строковый параметр `output-directory`: абсолютный путь к уже существующему **новому пустому каталогу**, например `C:/Temp/altova-19-run-001`. Это путь файловой системы, не `file:` URI. Передать его через API параметров или интерфейс выбранного процессора. Создаются `altova-19-default.img` и `altova-19-explicit.png`; повторный запуск в тот же каталог может перезаписать файлы. Без параметра шаблон должен завершиться ошибкой, пустая строка также отклоняется. Корпус не запускает запись автоматически.

`xbrl/taxonomy/fixture.xsd` и `labels.xml` — локальная синтетическая таксономия. Сохранить структуру каталога. Она импортирует официальную XBRL 2.1 schema по URI `http://www.xbrl.org/2003/xbrl-instance-2003-12-31.xsd`. Стандартные XBRL/XLink-схемы в корпус не скопированы: нужен XML catalog движка с локальными копиями либо сетевое разрешение стандартных схем. Поэтому весь сценарий не объявляется автономным/offline. Перед снятием эталонов проверить таксономию и `21-footnotes.xml` XBRL-валидатором целевой версии.

Для `xbrl-labels` URI таксономии вычисляется относительно base URI входного XML. При передаче XML из строки установить его исходный base URI. Для `xbrl-footnotes` передаётся исходный узел факта с сохранёнными связями документа.

В руководстве 2012 список функций называет `xbrl-footnotes`, а строка сигнатуры — `footnotes`. В корпусе используется `xbrl-footnotes`, также подтверждённое [официальным современным справочником](https://www.altova.com/manual/RaptorXML/raptorxmlserver/fxaltova_xsltgeneral.html). Имя на конкретном старом COM-сервере остаётся проверить; автоматическая подмена и заглушка отсутствуют. Неизвестная функция или ошибка разрешения таксономии не считаются успешным выполнением сценария.

Текущий `SaxonFoTransformer` не регистрирует эти расширения. Ошибка неизвестной функции до реализации совместимости ожидаема. Первые пять сценариев следует запускать непосредственно через XSLT-процессор, поскольку их результат не является FO.

Для статического аудита из корня репозитория:

```powershell
./eng/audit-xslt-functions.ps1 -TemplateDirectory ./test-data/altova
```

Ожидаются 21 шаблон, 0 ошибок разбора и 36 различных функций типа `Altova`. Этот аудит не компилирует XPath и не подтверждает runtime-семантику. Число сигнатур (46) учитывается отдельно в манифесте: скрипт объединяет перегрузки по имени.

В корпусе теперь есть вызовы всех 8 общих и 10 функций диаграмм из рассмотренных разделов AltovaXML 2012, а также 18 современных функций. Java-штрихкоды пока не покрыты. Это не полное покрытие всех параметров и граничных случаев. Наличие вызова подтверждает покрытие входного сценария, но не реализацию совместимости и не успешный запуск на Altova.
