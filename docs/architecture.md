# Архитектура и runtime

Библиотека ориентирована на .NET 8 / C# 12. Публичное пространство имён — `Company.XmlFo`.

## Слои

| Проект | Ответственность |
|---|---|
| Domain | `ConversionStage`, `ConversionException` |
| Application | `IXsltFoTransformer`, `IFoPdfRenderer`, `IXmlPdfGenerator` и `XmlPdfGenerator` |
| Infrastructure | SaxonCS, FOP/IKVM, подготовка изображений и DI |
| Demo | Пример с `PackageReference` на готовый NuGet |

Domain не зависит от движков. Application оркестрирует преобразование через интерфейсы. Infrastructure ссылается на Application, а Application — на Domain.

`XmlPdfGenerator` создаёт промежуточный FO рядом с целевым PDF и удаляет его в `finally`. Адаптеры публикуют результат атомарным перемещением временного файла. Ошибка или отмена до публикации сохраняет предыдущий результат.

## XSLT

`SaxonFoTransformer` использует SaxonCS-HE 13.0.0. Каждое задание получает собственный Processor; включения разрешаются относительно главного шаблона. Кэша нет. Доступ к внешним источникам и дополнительным выходным документам ограничен адаптером.

## PDF

`EmbeddedFopRenderer` вызывает Apache FOP 2.11 через IKVM 8.16.1 внутри процесса .NET. FOP, Batik и Java-зависимости компилируются при сборке библиотеки и включаются в NuGet. Maven SDK имеет `PrivateAssets=all`, а Maven-модель удаляется из пакета: потребителям не нужны Maven или повторная компиляция JAR.

Инициализация runtime выполняется один раз через `Lazy<T>`:

1. Проверяется платформа x64.
2. Во временный каталог извлекается DejaVu Sans и записываются настройки FOP.
3. На Linux загружаются нативные библиотеки из опубликованного приложения и настраивается Fontconfig.
4. При завершении процесса выполняется очистка временного каталога.

Нативные ресурсы упакованы в `runtimes/linux-x64/native`. Они не извлекаются в `/tmp`, поэтому рендерер работает с Docker `tmpfs /tmp`, запрещающим исполнение. `LD_LIBRARY_PATH` и Docker ENV не требуются. На Linux библиотека задаёт нативную переменную `FONTCONFIG_FILE` для процесса.

`FopProcessRenderer` сохранён как альтернативный адаптер существующей установки FOP. У него есть принудительный timeout и остановка дерева процессов. Встроенный рендерер удерживает слот до фактического завершения синхронного FOP, после чего проверяет отмену перед публикацией PDF.

## Изображения

Оба FOP-адаптера используют `FoImagePreparation`. Локальные и встроенные PNG проверяются, копируются с удалением `iCCP`, а ссылки в рабочем FO заменяются. Каталог задания удаляется при успехе и ошибке. PNG не декодируется и не перекодируется при удалении ICC.

Ограничения доверия, файлов и поддерживаемых платформ описаны в [README](../README.md).
