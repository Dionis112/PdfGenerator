# Архитектура и runtime

.NET 8 / C# 12, публичное пространство имён PdfGenerator. Domain содержит стадии и ошибки; Application — контракты запроса/результата, потоков, ресурсов и общий планировщик; Infrastructure — SaxonCS-HE 13, FOP 2.11/IKVM 8.16.1, кэши, профили и worker. Demo является отдельным NuGet-потребителем.

## Исполнение задания

DI регистрирует ScheduledXmlPdfGenerator. Он резервирует выходной путь, ограничивает активные полные цепочки и очередь, проверяет время ожидания и прекращает приём при shutdown. Движки получают отдельные семафоры для прямых вызовов адаптеров. Конфликт одного абсолютного выходного пути отклоняется; пути с разным регистром совпадают на Windows. Прямые конструкторы генераторов допускают явное оборачивание планировщиком.

XmlPdfGenerator подготавливает временный FO и PDF. Файл публикуется атомарным перемещением на том же файловом разделе после успешного рендеринга, проверки PDF и отмены. Ошибка до публикации сохраняет прежний файл. Готовый PDF копируется в caller-owned Stream без перемотки и закрытия; финальное копирование не атомарно.

Источники читаются с текущей позиции без Seek. PreparedXmlSource ограничивает чтение и держит до 256 КиБ в памяти, затем переносит снимок на диск. Это не превращает построение дерева Saxon в streaming XSLT. Настройки сервисов — immutable records; параметры и допустимые корни копируются в запрос.

## Кэши

StylesheetSnapshot копирует основной XSLT и транзитивные include/import, учитывает xml:base и политику локальных корней. Ключ SHA-256 включает URI, содержимое каждого снимка и идентичность Saxon. Компилятор читает те же копии, которые хешировались. Runtime-resolver executable запрещает внешние ресурсы. Значения параметров не входят в ключ.

XsltTemplateCache сохраняет Processor и immutable XsltExecutable; отдельный transformer, вход, параметры и результат создаются на задание. Одновременные запросы одного ключа ожидают одну компиляцию. Отмена ожидателя не отменяет общую компиляцию. Ограничены записи, оценочные байты, активные и ожидающие компиляции; завершение сервиса ждёт общие задачи. LRU/idle TTL вытесняют неиспользуемые записи. Ошибка компиляции удаляется при следующем обращении; WarmupAsync и ClearTemplateCache доступны явно.

FopFactoryCache хранит снимки конфигурации и явных файлов шрифтов, учитывая содержимое в ключе. Ограничены число фабрик и оценочные байты. Lease удерживает ресурсы до завершения документа; активные фабрики не вытесняются. newFop сериализуется на фабрике из-за ленивых изменений Xerces DOM; длительный layout выполняется параллельно. FOUserAgent, listener, layout и выход создаются на документ. Отложенные image sources закрываются, image cache очищается после рендеринга, чтобы не накапливать уникальные URI и дескрипторы.

## FO, изображения и шрифты

FO переписывается последовательно XmlReader/XmlWriter с буфером текста 64 КиБ. Значения data URI читаются частями; декодирование base64/percent идёт на диск. XmlReader всё равно может удерживать отдельное большое значение атрибута. PNG проверяется по структуре и CRC, iCCP удаляется без декодирования пикселей. Повторные изображения используют снимки внутри задания; локальный оригинал не меняется. SVG обрабатывается рекурсивно с ограничением глубины 16.

Квоты ограничивают отдельный файл, число уникальных изображений, суммарные байты изображений и накопленные записи временной подготовки (включая уже удалённые промежуточные копии). Исходный FO и PDF входят в квоту рендеринга; PDF writer отклоняет запись до превышения оставшегося бюджета. Входные снимки, кэши и рендеринг имеют отдельные бюджеты; это не единая квота всего раздела. Нужен дополнительный запас диска для подготовленных XML/XSLT, профилей и runtime. Ошибки реального диска завершают задание и сохраняют предыдущий результат.

LocalResourcePolicy нормализует пути, разрешает только локальные файлы в заданных корнях и запрещает сеть, UNC, symlink/reparse points. По умолчанию зависимости разрешены внутри каталога шаблона; xml:base не расширяет права. DTD, внешние XSLT-функции, doc/document, unparsed-text, коллекции и result-document запрещены. Это ограничения ресурсов, а не песочница для недоверенного кода.

PdfProcessingProfile владеет копиями шрифтов и конфигурации, проверяет font metadata при создании и вычисляет стабильную версию по содержимому и настройкам. Пересоздание профиля даёт новые записи кэша. FO использует явные font-triplets. Внутри процесса SVG ограничен встроенным DejaVu. Пользовательские SVG/AWT-шрифты регистрируются только в изолированном worker соответствующего пула; family aliases преобразуются в физические имена. CSS font/font-family в SVG отклоняются. Отсутствующее FO-начертание даёт обычную подстановку и код предупреждения.

## Worker и доставка

Infrastructure.dll имеет .NET entry point --pdf-worker. Тот же NuGet содержит runtimeconfig и deps.json; buildTransitive/PdfGenerator.targets копирует их при build/publish. Потребитель сохраняет один PackageReference. FOP/Batik и Java-зависимости скомпилированы заранее; Java, Maven и внешний FOP при исполнении не требуются. Framework-dependent запуск использует установленный dotnet host. Single-file/trimming не поддерживаются.

Родитель создаёт каталог пула и каталог задания, переносит XML/XSLT в ограниченные файлы и передаёт по stdin только метаданные, пути, QName/тип/lexical параметры. Протокол JSON lines версии 1 ограничен 1 МиБ символов; handshake сверяет версии протокола и движков. Stdout принадлежит протоколу и непрерывно вычитывается в очередь не более четырёх ответов; переполнение и повреждение завершают обмен. Worker не пишет в stdout в простое. Stderr непрерывно вычитывается и отбрасывается, чтобы не блокировать процесс и не раскрывать данные. Повреждённые, слишком большие и оборванные сообщения отклоняются.

Пул ограничен MaxWorkers и резервом MemoryBudgetBytes. Одно задание на процесс; выбор свободного worker учитывает affinity URI шаблона. Процессы сохраняют кэши, проверяются ping/pong и перезапускаются после заданного числа документов. Повторный сбой запуска имеет backoff и предел попыток; автоматического retry документа нет. TEMP/TMP/TMPDIR дочернего процесса указывают в собственный каталог экземпляра worker внутри пула. Родитель удаляет runtime, шрифты, снимки и временные входы после выхода, включая принудительное завершение. После result родитель проверяет JobId, число страниц, размер и PDF header, затем публикует результат.

Очередь, старт и исполнение имеют отдельные тайм-ауты. Отмена запрашивает stop, затем после короткого grace period убивает дерево и ждёт подтверждения завершения. Слот освобождается после этого и очистки. Startup/protocol/crash/timeout/наблюдаемое превышение памяти различаются; недоказанный crash не называется OOM. Shutdown перестаёт принимать задания, ждёт grace period и отменяет оставшиеся.

## Память и платформа

MaxWorkingSetBytes проверяется родителем каждые 100 мс: это наблюдение, а не строгий лимит ОС. MemoryBudgetBytes проверяет резерв процессов. Windows Job Objects позволяют hard limit, но требуют отдельной интеграции жизненного цикла; в Linux индивидуальные cgroups требуют доступного делегированного writable cgroup tree, которого нет в проверяемом non-root/read-only контейнере. Текущий переносимый режим — наблюдение и внешний контейнерный hard limit вместе с ограничением конкуренции. Изоляция процесса гарантирует возможность остановки движка, но не песочницу.

Поддержаны Windows x64 и Debian 12/glibc x64. Runtime извлекает шрифты во временный каталог один раз; Linux native assets находятся в опубликованном приложении, поэтому /tmp может быть noexec. Fontconfig на Linux получает конфигурацию встроенных шрифтов. Пользовательские профили не меняют глобальную конфигурацию процесса для каждого задания. Runtime-контейнер не устанавливает apt/Java/Maven и преобразует при network none.

Платформенные механизмы изучены по первичным источникам: [Windows Job Objects: process/job committed-memory limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information), [Linux cgroup v2: delegation и memory.max](https://docs.kernel.org/admin-guide/cgroup-v2.html). Сохранён переносимый режим наблюдения с внешним лимитом контейнера; отдельная интеграция строгого лимита на процесс в этот выпуск не входит. Закрытие отложенных image sources соответствует [XML Graphics image-loader lifecycle](https://xmlgraphics.apache.org/commons/image-loader.html).
