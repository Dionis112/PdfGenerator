# План развития PdfGenerator после MVP 0

Дата исходного плана: 2 октября 2026 года. Реализация: 4 октября 2026 года. Этапы API, кэшей, streaming-подготовки FO, ограниченного планировщика и bundled worker выполнены. Контрольный корпус синтетический; расширение реальными обезличенными шаблонами зависит от их появления. Single-file/trimming, другие RID, универсальный индивидуальный hard memory limit, streaming XSLT и побайтовая детерминированность не заявлены.

Проверки и бюджеты: [тестирование](testing.md), [результаты нагрузки](performance.md), исходные JSON в docs/benchmarks. Численные бюджеты являются исходными критериями этого этапа для синтетического корпуса.

План раскрывает три направления: **2 — удобный API**, **4 — скорость и повторяемость**, **5 — изоляция тяжёлых заданий**. Основной сценарий — большие XML и документы, входные данные размером в десятки мегабайт, повторные преобразования и работа в контейнере без установки дополнительных системных компонентов.

## 1. Общие требования и исходная точка

### 1.1. Требования к результату

- Сохранить текущую цепочку XML + XSLT → FO → PDF, поддержку PNG с удалением `iCCP`, прозрачности, SVG и кириллицы.
- Сохранить существующий `GenerateFileAsync` и стандартный сценарий подключения NuGet.
- Обеспечить обработку больших документов с явными ограничениями памяти, файлов, очереди и времени.
- Повторные задания с одним шаблоном должны использовать подготовленные ресурсы; данные и параметры каждого задания должны оставаться изолированными.
- Ошибка, отмена или аварийное завершение не должны публиковать частичный PDF или уничтожать предыдущий результат.
- Worker должен поставляться вместе с необходимыми ресурсами через NuGet. В поддерживаемом стандартном .NET runtime контейнере не требуются `apt`, Java, Maven или внешний FOP.
- Сохранить текущую поддержку Windows x64 и Linux x64. Другие RID и образы, включая Alpine/musl, требуют самостоятельной проверки и не входят автоматически в этот этап.

### 1.2. Текущие ограничения, которые нужно устранить или явно учитывать

- `XmlFoOptions.MaxInputBytes` по умолчанию равен 16 МиБ; FO и PDF ограничены 64 МиБ, отдельное изображение — 32 МиБ.
- Saxon Processor и скомпилированный XSLT создаются для каждого задания.
- FopFactory создаётся для каждого рендеринга.
- `FoImagePreparation` читает FO целиком в `XDocument`; встроенные изображения могут создавать дополнительные буферы.
- Для Saxon и встроенного FOP отмена проверяется вокруг синхронной операции. Она не гарантирует остановку вычисления внутри движка.
- Ограничения размеров файлов не задают верхнюю границу памяти процесса.
- Проверка функциональности уже существует; численные обязательства по скорости и памяти пока не установлены.

### 1.3. Значение повторяемости

1. **Функциональная:** одинаковые входы, шаблон, параметры, шрифты, ресурсы и настройки дают одинаковые страницы, текст и визуальное содержание.
2. **Эксплуатационная:** серия заданий не вызывает накопления ресурсов; после прогрева задержка и потребление памяти остаются в измеренном диапазоне.
3. **Побайтовая:** отдельно проверить даты, идентификаторы PDF, метаданные и функции XSLT, зависящие от времени. Не обещать совпадение SHA-256 PDF до реализации и проверки отдельного детерминированного режима.

## 2. Направление 2: API для реального использования

Реализованы `ConversionRequest`, `ConversionResult`, `XmlSource`, `XsltParameter`, `LocalResourcePolicy`, `PdfProcessingProfile` и перегрузки `GenerateAsync`. Старый файловый метод — обёртка над новым контрактом. Проверки и примеры использования находятся в `RequestApiTests` и README.

Оба режима зарегистрированы в DI. Worker поставляется одним PackageReference с runtimeconfig/deps. Профили копируют и проверяют шрифты, имеют неизменяемую версию; пользовательские SVG/AWT-шрифты выполняются в отдельном пуле worker. LargeXml допускает 64 МиБ с одним активным заданием. Граничные 100 МиБ измеряются с явным лимитом 128 МиБ.

- [x] На первом этапе разрешать одно активное задание в каждом worker: остановка процесса не затрагивает другой документ.
- [x] При отмене запросить корректную остановку; после ограниченного grace period завершить процесс и дождаться подтверждения завершения.
- [x] Отсчитывать жёсткий timeout в родительском процессе, независимо от состояния синхронного движка.
- [x] Считать слот освобождённым только после завершения worker и очистки ресурсов; вместо аварийного worker запускать новый.
- [x] Для памяти различать наблюдение working set/RSS и строгий лимит ОС. Исследовать Windows Job Objects и доступные Linux/cgroup механизмы с учётом прав внутри контейнера.
- [x] Если индивидуальный строгий лимит worker недоступен, явно сообщать режим контроля и использовать контейнерный лимит вместе с ограничением конкуренции. Не обещать универсальный hard memory limit из NuGet.
- [x] Классифицировать timeout, отмену, crash и наблюдаемое превышение памяти отдельно; при отсутствии доказательств не называть любой crash OOM.

Критерий готовности: зависший Saxon/FOP прекращается без остановки приложения; авария не публикует результат; ограничения и доступный режим контроля описаны для каждой платформы.

### 4.4. Пул и сохранение преимуществ кэша

- [x] Начать с прототипа одного задания на один процесс, измерить накладные расходы, затем реализовать долгоживущий ограниченный пул.
- [x] Сохранять кэши XSLT и FOP внутри каждого worker; определить маршрутизацию шаблонов с учётом прогрева и справедливости очереди.
- [x] Настроить верхний предел worker-процессов из общего бюджета памяти, а не только числа CPU.
- [x] Перезапускать простаивающий worker по измеренному порогу памяти или числу заданий; учитывать стоимость нового прогрева.
- [x] Добавить health check, предел повторных запусков и задержку при повторяющемся сбое запуска.
- [x] Не повторять автоматически любое упавшее задание. Определить ограниченную политику retry только для подходящих инфраструктурных ошибок с сохранением атомарности.
- [x] Реализовать graceful shutdown: прекратить приём, завершить задания в установленный срок, затем остановить оставшиеся процессы.

Критерий готовности: пул даёт измеримый выигрыш по повторным заданиям, не превышает бюджет процессов и восстанавливается после timeout/crash.

## 8. Решения, которые нельзя принимать без проверки

- Повышение размера XML не доказывает, что хватает памяти для соответствующего дерева и результата XSLT.
- Вход через Stream и чтение FO через XmlReader не гарантируют потоковую обработку движком. Поддержку XSLT streaming нужно отдельно проверить для используемой редакции SaxonCS; она не является обязательной предпосылкой этого плана.
- Прямую передачу FO в FOP, дополнительные профили шрифтов и режим побайтовой повторяемости принимать по результатам прототипов.
- Значения timeout, размеров кэша, числа worker и лимитов больших документов выбирать из baseline и целевого бюджета ресурсов.
- Отдельный процесс обеспечивает возможность принудительного завершения, но сам по себе не является песочницей для недоверенных шаблонов.

## 9. Итог принятых решений

- XSLT: immutable executable/Processor из bounded snapshot cache, отдельный transformer и параметры на job. Общая компиляция не отменяется отдельным ожидателем; задачи учитываются до завершения.
- FOP: immutable config/font snapshots, lease и bounded factory cache. Инициализация newFop сериализована из-за Xerces; layout параллелен. Image sources и image cache завершаются на документ.
- FO остаётся файлом: buffered Stream дал те же 167 страниц, устойчивого ускорения не показал и добавил удерживаемый буфер. Файлы облегчают ограничения ресурсов, подготовку картинок, диагностику и атомарную публикацию.
- Worker: JSON lines v1 для метаданных; file staging, handshake/health check, hard timeout/cancel, warmed pool, affinity, recycle, startup backoff/circuit, graceful shutdown. Retry документа отсутствует.
- Память: наблюдаемый RSS/working set, резерв пула и внешний контейнерный hard limit. Короткий overshoot возможен. Windows Job Objects/Linux cgroups требуют отдельной интеграции и прав; универсальная NuGet-гарантия не заявлена.
- Baseline до оптимизаций сохранён для 10 МиБ; полная матрица контроля без переиспользования сохраняет итоговую streaming-подготовку и не выдаётся за исходный MVP. Матрицы 10/25/50/100 и 1/2/4, холодные/повторные/новые/смешанные/Stream сценарии и длительный прогон публикуются с конфигурацией.
- Производственные шаблоны не предоставлены. Их добавление — условное пополнение корпуса, а не гарантия любых документов такого же размера.
