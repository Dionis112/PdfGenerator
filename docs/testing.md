# Тестирование

## Приёмка общего профиля AltovaXML 2012

```powershell
$run = Join-Path 'artifacts/altova2012-acceptance' ([Guid]::NewGuid().ToString('N'))
dotnet run --project eng/PdfGenerator.TemplateValidation -c Release -- . $run --strict-altova2012
```

Используйте новый пустой каталог. Стенд проверяет шесть общих и три отрицательных примера, банковский комплект 2012 на четырёх входах, отключённый кэш и холодное/повторное выполнение с кэшем. XDM проверяется до сериализации; worker выполняет семантические утверждения внутри исходного шаблона перед PDF. Банковские суммы, даты, нумерация и клиент проверяются независимо. Повреждённый результат и отсутствующая функция проверяются контрольными отказами стенда. Для отрицательных evaluate требуется этап Transform и конкретный код; XPST0017 не засчитывается. `acceptance.json` содержит результаты, хэши зависимостей, версию профиля/движка и время выполнения; любое нарушение даёт ненулевой exit code.

Ожидания и допуски находятся в `test-data/altova/expected-properties.json`. Это проверка по документации, а не эталоны Altova. Полные ограничения — в [описании реализации](altova-2012-implementation.md). Исследовательский запуск без `--strict-altova2012` сохраняет отключённый профиль и собирает неподдержанные вызовы всего корпуса.

## Полная проверка

```powershell
./eng/verify.ps1
./eng/verify.ps1 -DependencyFeed "$env:USERPROFILE/.nuget/packages"
./eng/verify.ps1 -Docker
./eng/format.ps1 -Check
```

verify проверяет двуязычные XML summary/param/returns/exception, запускает модульные и интеграционные тесты и 70 строгих проверок общего профиля Altova. Затем собирает три NuGet-пакета, восстанавливает Demo в отдельный новый каталог пакетов, выполняет self-test и повторяет его после publish. Отдельный каталог исключает использование старого содержимого при одинаковой preview-версии. DependencyFeed позволяет читать уже скачанные сторонние пакеты из локального cache. В Docker потребитель также использует свежий каталог и опубликованные пакеты.

Текущий состав: 6 модульных и 116 интеграционных сценариев. Модульные проверки подтверждают передачу аргументов, отмену, очистку, ограничения очереди, конфликт выходного пути, queue timeout, освобождение reservations и graceful shutdown. Интеграционные проверки используют настоящие Saxon/FOP.

## Свежая проверка всего корпуса XSLT

```powershell
dotnet run --project eng/PdfGenerator.TemplateValidation -c Release -- . artifacts/template-validation/my-run
python eng/verify-template-pdfs.py artifacts/template-validation/my-run
```

Каталог результата должен быть пустым или новым. `pypdf` нужен только для независимой проверки PDF второй командой. Стенд сверяет инвентарь всех `.xsl`/`.xslt` в `test-data` с перечнем сценариев и требует добавить сценарий для нового шаблона. Кэш отключён; каждый пример выполняется внутри процесса и через worker. Общий корень `test-data` явно разрешён для локальных include/import; сетевой доступ не разрешается. Модуль `basic/parts/layout.xsl` отдельно компилируется и выполняется в составе `basic/document.xsl`.

Результаты: `results.json` с хэшами входов и главных XSLT, `report.md`, отдельные статические аудиты, FO и PDF. Файлы `.pdf` неуспешных сценариев содержат контрольную строку прежнего результата: так проверяется атомарность публикации; это не готовые PDF. Статический аудит имеет собственные ограничения на переходы include за пределы каталога шаблона, поэтому его замечания нужно отличать от результата выполнения с явно разрешённым общим корнем.

`unsupported-functions` означает Compile/XPST0017; `negative-prerequisite-missing` означает, что отрицательный пример не дошёл до ожидаемой ошибки выполнения. Код 0 подтверждает завершение измерений и прохождение контрольных сценариев, а не полную совместимость с Altova. Неожиданные ошибки, различие статусов режимов, замена прежнего файла при ошибке или предупреждения о недостающих глифах дают код 1. Все банковские сценарии дополнительно проверяются по содержимому FO и количеству страниц.

Снимок результатов и границы проверки: [template-validation-2026-10-06.md](template-validation-2026-10-06.md).

## Очистка результатов сборки

После проверок можно выполнить `./eng/clean.ps1 -VerificationCache -WhatIf`, затем `./eng/clean.ps1 -VerificationCache`. Скрипт очищает `bin/obj/TestResults` проектов, временные feeds потребителя, сгенерированные NuGet-конфигурации и публикацию Demo. Пакеты, отчёты приёмки и FO/PDF сохраняются. Для следующего полного прогона запускайте `verify.ps1`; проверку форматирования с `--no-restore` выполняйте после восстановления зависимостей.

## Покрытие автоматических тестов

- Старый файловый API и запросы, QName, string/bool/integer/decimal/DateTimeOffset, отсутствие/пустая строка и параллельная изоляция параметров.
- Stream без Seek/Length, переход буфера на диск, превышение лимитов, ошибки чтения/записи, отмена, caller-owned lifetime и base URI/include.
- Версия/снимок шрифта профиля, кириллица, страницы, предупреждения, локальная политика ресурсов, запрет сети, DTD и внешних XSLT-операций.
- PNG/iCCP/CRC, альфа-канал, base64/percent URI, локальные картинки, nested SVG, активный SVG и небезопасные CSS-ссылки.
- Общая компиляция, изменение транзитивного include/import, bounded cache, восстановление после ошибки, отмена отдельного ожидателя, изменение конфигурации FOP и параллельное использование фабрики.
- Квоты PDF во время записи, число изображений, временный диск, сохранение предыдущего результата и очистка промежуточных файлов.
- Реальный worker: переиспользование процесса, внешний crash и восстановление, жесткий timeout и отмена бесконечного XSLT, typed Stream protocol, превышение наблюдаемой памяти, startup circuit, oversized/incompatible protocol, recycle и пользовательский SVG-шрифт.
- Диагностики Saxon: коды и позиции ошибок компиляции/выполнения в обоих режимах, предупреждения при повторном использовании кэша, изоляция параллельных заданий, ограничение числа предупреждений и сохранение ошибки после достижения лимита. Пользовательские имена ошибок, текст документов и пути не входят в диагностики.
- Корпус `sales/`: строки таблицы, суммы позиций и итог 26 650 000 в версиях XSLT 1.0/2.0, кириллица, колонтитул, пустой отчёт и полный рендеринг PDF внутри процесса и через worker.

Self-test NuGet-потребителя проверяет FO/PDF, Stream+параметры+include, число страниц/байты и bundled worker. PNG с повреждённым ICC и прозрачностью, SVG с текстом и Gaussian blur выполняются без внешнего FOP.

## Контейнер

```powershell
docker build -t pdfgenerator .
docker run --rm --read-only --tmpfs /tmp:rw,noexec,nosuid,size=512m --network none --memory 2g --cpus 4 pdfgenerator --self-test --pdf --output /tmp/smoke
```

Build запускает тесты, пакует NuGet и делает framework-dependent publish linux-x64. Runtime — стандартный .NET 8 Debian 12/glibc x64, non-root, без apt/Java/Maven. Worker получает граф зависимостей потребителя после publish, поскольку IKVM RID assets размещаются иначе, чем при обычном build. Runtime не требует сети. Single-file/trimming и другие RID не заявлены.

## Нагрузка и критерии

```powershell
./eng/benchmark.ps1
./eng/benchmark.ps1 -Mode worker -Sizes 10,50 -Concurrency 1,2,4
./eng/benchmark.ps1 -Scenario baseline
./eng/benchmark.ps1 -Scenario mixed -Sizes 10 -Concurrency 2 -Iterations 20
./eng/benchmark.ps1 -Scenario stream -Mode worker -Sizes 10 -Concurrency 1
./eng/benchmark-container.ps1
```

Стенд генерирует XML 10/25/50/100 МиБ, grouping/sorting/keys, многостраничную таблицу, 20 повторных PNG с ICC и SVG. Фактический размер записан в JSON. Scenario baseline создаёт новые экземпляры адаптеров на задание; это контроль без переиспользования, сохраняющий итоговую streaming-подготовку FO. Исторический замер до оптимизаций хранится отдельно.

JSON содержит runtime/OS/движки/шрифт, настройки, структуру корпуса, холодный и прогретые вызовы, этапы, queue wait, p50/p95, throughput, peak RSS/heap, GC/allocations, временные байты и кэши. Для worker peak RSS суммирует parent+children; peak managed heap относится к parent, child GC/caches доступны в EngineCounters. Выборка каждые 50 мс является наблюдением и может пропустить короткий пик. Сборщик файлов допускает исчезновение каталогов между чтениями.

Полные отчёты и бюджеты — [performance.md](performance.md). Реальных обезличенных шаблонов пока нет; согласованные профильные бюджеты относятся к синтетическому корпусу, а не произвольным XML/XSLT.

## Независимая проверка PDF

Для проверки текста и изображений используется pypdf, для визуального контроля — Poppler pdftoppm. Сравниваются страницы, извлечённый текст и данные изображений после холодного старта, прогрева, контрольного запуска, worker и Linux; metadata/даты PDF исключены из побайтовой гарантии. Пример сравнения и JSON-результат находятся в docs/benchmarks.

```powershell
pdftoppm -scale-to 1200 -singlefile -png result.pdf artifacts/preview
```

Для производственных шаблонов добавляйте свои эталонные PDF, проверку текста, изображений, переносов и layout. Публичный корпус синтетический.
