# Предварительное сопоставление функций Altova и SaxonCS

Дата: 2 октября 2026 года. Это инвентаризационный список, а не утверждение о совместимости производственных XSLT. В репозитории пока есть только синтетические шаблоны. Для фактического списка нужны рабочие XSLT и все их `xsl:include`/`xsl:import`.

В предоставленной `Altova.AltovaXML.dll` указана версия 12.3.0.0. Для перечня собственных функций использована документация AltovaXML 2012, близкая к эпохе библиотеки; версия установленного COM-сервера пока неизвестна. Префикс `altova` условен: идентификатор функции определяется **URI пространства имён** `http://www.altova.com/xslt-extensions` и локальным именем.

| Функция/семейство Altova | Возможный путь в SaxonCS | Трудоёмкость/оговорка |
|---|---|---|
| `altova:evaluate(xpath, ...)` | Для доверенного XSLT: переработать на XSLT 3.0 `xsl:evaluate` (есть в Saxon-HE 13). | Высокая. Это инструкция, а не замена имени функции; проверить контекст, пространства имён, переменные `$p1...`, base URI и разрешённые ресурсы. `saxon:evaluate()` требует PE/EE и тоже не является автоматической подменой. |
| `altova:distinct-nodes(nodes)` | `xsl:for-each-group` с проверкой `deep-equal()` либо отдельная интегрированная функция C#. | Средняя/высокая. Altova удаляет **структурно равные узлы**; `distinct-values()` сравнивает атомарные значения и не равноценна. Проверить порядок и то, какой исходный узел сохраняется. |
| `altova:encode-for-rtf(...)` | Удалить при переходе на FO или реализовать C# функцию при доказанной потребности. | Низкая для чистого FO-пути; не считать обычным XML escaping. |
| `altova:generate-auto-number(...)`, `altova:reset-auto-number(...)` | `xsl:number`, позиция/группировка; если состояние по ID и сбросы существенны — отдельная реализация с состоянием на одну трансформацию. | Высокая. `xsl:number` не воспроизводит произвольные побочные эффекты и reset автоматически. Нужны эталонные результаты и тест параллельных запросов. |
| `altova:get-temp-folder()` | Передавать путь временного каталога параметром приложения либо зарегистрировать контролируемую C# функцию. | Средняя. Текущий API параметров ещё не реализован. Путь Altova/Windows нельзя механически переносить в контейнер. |
| `altova:xbrl-labels(...)`, `altova:xbrl-footnotes(...)` | Отдельный XBRL-компонент или предварительная подготовка данных. | Высокая. Прямой функции Saxon-HE нет; нужна таксономия и проверка лицензии/данных. |
| Функции диаграмм и штрихкодов Altova | Генерировать SVG/PNG до XSLT или использовать специализированный C# компонент. | Высокая. Требуются проверка конкретных вызовов, форматов, лицензии и того, как FO ссылается на изображения. |
| Вызовы пользовательских .NET/Java функций, `msxsl:script` | Явно реализованные и зарегистрированные функции C# с теми же QName и сигнатурами либо перенос вычисления перед XSLT. | Зависит от кода. Не активировать произвольные вызовы платформы; действующая реализация запрещает внешние функции и не регистрирует совместимые. |

## Что обычно переносится без функции-адаптера

Вызовы в стандартных пространствах имён `http://www.w3.org/2005/xpath-functions` (`fn:`) и `http://www.w3.org/2001/XMLSchema` (`xs:`), а также стандартные инструкции XSLT 2.0 поддерживаются SaxonCS-HE на уровне языка. Примеры: `string-join()`, `format-date()`, `format-number()`, `deep-equal()`, `current-group()`, `xsl:for-each-group`. Всё равно проверить результат на эталонах: AltovaXML документирует особенности схемной типизации и обработки пробельных узлов.

`xsl:function` с пользовательским пространством имён — это функция, написанная в самом XSLT. Её не следует ошибочно относить к встроенным функциям Altova. Проверять объявление и все импортированные модули.

## Текущее состояние пакета

`SaxonFoTransformer` создаёт новый `Processor`, задаёт `ALLOW_EXTERNAL_FUNCTIONS=false` и не регистрирует функции совместимости Altova. Поэтому нельзя считать, что любой вызов `altova:*` будет выполнен. Интегрированные функции SaxonCS можно зарегистрировать по QName через C# API, но для этого сначала нужно установить точный набор вызовов и ожидаемую семантику. Динамическое `xsl:evaluate` и обращения к ресурсам требуют отдельного решения по политике доступа.

## Как превратить список в план реализации

1. Вызвать библиотечный `IXsltDiagnostics.AnalyzeFile(path)` для каждого главного XSLT: он просмотрит локальные include/import, вернёт функции и их статус, ошибки и предупреждения. Для текста XSLT без файла использовать `Analyze(xslt)`. Результат оставить в закрытой среде. Консольный доступ: `dotnet run --project PdfGenerator.Demo -- --diagnose-xslt C:\path\to\document.xsl`. Ранее добавленный `eng/audit-xslt-functions.ps1` остаётся упрощённым независимым скриптом, если пакет установить нельзя.
2. Составить таблицу `URI + local-name + число аргументов → файл/строка → число вызовов → предлагаемый аналог`.
3. Скомпилировать шаблоны текущим пакетом и зафиксировать все ошибки, затем для каждого вызова выбрать переписывание XSLT, подготовку данных или C# функцию совместимости.
4. Проверить каждое решение на эталонных XML и FO/PDF от действующей системы, включая пустые значения, даты, локали и параллельные запросы.
